# v2 修复循环 25 轮迭代的教训

2026-07-25 从 sgp-dev 的 codex session（`storyos` 仓库 `codex-run` 分支，
`702bcde..dc66b77`，约 26 小时，约 30 个 commit）中抢救出来，之后该 session 已停止。
代码属于 v3 要替换掉的架构，所以一行都不合并。**失效模式分类**才是资产：每一条都是
typed-state 门控修复循环的一种精确刻画的破坏方式，在真实运行上复现过、带 journal 哈希。
一手来源是远端的 `storyos/docs/11-iteration-log.md`，它留在 `storyos` 仓库里。

## 元教训

那些迭代无一例外是用**"gate 是否通过 / 任务能否跑完"**验证的。一次都没算过 CED。
26 小时的工程投入优化的是门通过率，而那不是论文被评判的量；本地的实测（CED 4.690 vs
bare 4.100）已经说明门通过率和质量早就脱钩了。

由此得到 v3 的两条设计规则：

1. **每一次引擎迭代在被称为"改进"之前，必须在评测指标上打分。** 让运行跑完但不改变 CED
   的改动是可靠性修复，必须如实标注为可靠性修复。
2. **一个失效模式需要 25 次连续微修复的验证循环，形状本身就是错的。** 这些修复从未收敛：
   每修一个就暴露下一个边界。这是关于架构的证据，不是关于投入的证据。

## 分类

### A. 引擎改写 agent 的提案 —— 占主导的失效族

v2 有一批确定性"保留助手"，会把 writer 的原始 patch 与上一次被拒尝试中带过来的材料合并。
它们造成了观察到的两个代价最高的死局：

- **正文回滚循环。** 只要某个不相关的、被带过来的 fact-ref 要求已被满足，
  `_preserve_exact_repair_text` 就会把之前被拒的正文恢复回去。在
  `tuning-v2-disk-recovered-r1` 中，场景 8 的九稿**正文摘要完全相同**：质量评审指出一个
  人名连续性笔误，writer 改对，助手把它改回去，无限循环。
- **事实与授权复活。** `_preserve_unaffected_knowledge_grants` 为 writer 已刻意删除的
  fact 恢复了授权，随后引用闭包又把这个 fact 本身恢复了。某场景的第 4–7 稿和第 9 稿都因此
  卡在同一个 temporal 重叠上。

**v3 规则：** 引擎绝不部分改写 agent 的提案。它只能接受、带 findings 拒绝、或要求重新提一份。
任何合并都是 writer 自己的活，在 writer 自己的回合里做，在 transcript 里可见。

### B. 重复抽取的非确定性

同样的正文重新做 audit 会得到不同的 claim 集合（`cli-8k-20260724-a`）。修法是把 audit 缓存
绑定到 `(精确文本, 排序后的 present_characters)`。但这个缓存键随后自己变成了下一个失效模式（C）。

**v3 规则：** 任何参与门控的 LLM 抽取都必须有显式缓存键，而且这个键必须对无关元数据保持稳定。

### C. 元数据漂移导致缓存失效

正文不变，但 writer 给出的 `present_characters` 列表在候选之间从 4 个名字涨到 5 个再到 6 个。
每次变化都让 audit 缓存失效、产生新的 audit 引用、生成新的 findings——一个没有不动点的循环，
直到引擎被教会"只允许一次在场修正，之后冻结"为止。

**v3 规则：** 要么从正文确定性地推导在场角色，要么把它当作草稿的一部分（改它就等于新草稿），
绝不能让它作为自由浮动的元数据去悄悄改变缓存键。

### D. 修复反馈的聚合粒度

反复出现的模式：findings 按 claim 逐条报告，writer 按 claim 逐条动作，而仓库的完整性约束是
按实体的。

- 五条独立 claim 都指向 active fact 53 → writer 写了五次 `supersedes_fact_id: 53` →
  单后继约束把整批都拒了。需要按冲突 fact id 分组。
- 同一 patch 内某个 `(subject, predicate)` 槽位的 temporal 冲突按两两报告 → writer 合并了
  一部分、保留了另一部分 → 重叠仍在。需要按槽位分组。

**v3 规则：** 反馈要聚合到"修复动作必须在其上发生"的粒度，那个粒度是实体，不是单条 finding。

### E. findings 相互遮蔽

一个非结构性的 outline parent 引用错误短路了 epistemic、temporal、contract、semantic 四个
validator，于是修复处理了那个琐碎错误，两个 epistemic 错误一直藏到下一轮才浮现
（`cli-8k-20260724-b`）。

**v3 规则：** 只有真正格式错误的输入才允许短路后续检查。其余全部照跑、一起报告，让一轮修复
看到问题的全貌。

### F. 精确身份字符串的脆弱性

以精确身份字符串为键的修复要求，会因为字符级的引号漂移而失效：writer 保留了 fact 及其授权，
但把身份字符串用不同的引号字符重打了一遍，造成 audit 碰撞。后续的正文修订又在固定修复预算内
来不及了。

**v3 规则：** 身份是对规范化文本取的内容摘要，绝不是要模型逐字节复现的原始字符串。

### G. 在途调用与 fail-closed 记账

进程被中断会留下 reserved 状态的调用记录；严格记录器随后会拒绝之后的每一次调用，而且没有协议
去结算它们。DOME 那边把同样的情形建模为 `AmbiguousInFlightCall`，但 StoryOS 的记录器没有等价的
终态或安全重放路径。为此人工做过两次归档—重启干预。

**v3 规则：** 在任何长跑之前，先定义显式的 ambiguous-in-flight 终态，并写明结算/重放流程。

### H. 环境

根文件系统在批次运行中途写到 100%，三个 cell 以 `OSError` 死掉，一整个 paired 轮作废。对应的
处置——启动前预检至少 3GB 空闲、低于 1GB 就中止——值得保留。

## 值得复用的东西

- **预注册纪律。** 每轮迭代全新 run identity、禁止拼接 partial 轮、逐字节可重建的 source lock、
  每次运行都带 frozen-config 摘要。这是远端工作中真正严谨的部分，v3 应当整体继承。
- **3M token / 20k writer cap 配置**，本地 14/19 完成率就是靠它才成为可能。
- **1020 → 1764 的确定性换题**，用于化解 content-filter 死局，带完整授权链。
- **sgp-dev 上的 `~/storyos-data/scores/`**：七个已打分的 baseline 系统，数字与本地一致。

## 不值得复用的东西

引擎 diff 本身。它们是对 `orchestrator.py`、`verifier.py`、`audit.py` 的补丁，所处架构把
canonical state 放在 SQLite 表里、并且让引擎改写 writer 的 patch——这正是 v3 明确反转的两个
决策（`02-architecture.md` §3，以及上面的规则 A）。
